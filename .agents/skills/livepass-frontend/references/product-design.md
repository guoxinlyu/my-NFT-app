# 1 背景与目标

## 1.1 问题从哪来:四个结构性痛点

演唱会票务的问题不是「某一家平台做得不好」,而是**中心化数据库 + 供需失衡**共同产生的结构性问题。调研(`docs/related-works/`)确认了四个痛点,并给出了每个痛点的证据锚点:

| 痛点 | 典型表现 | 证据锚点(来源/证据等级) | 链上设计的切入点 |
|---|---|---|---|
| **P-A 黄牛与机器人抢票** | 放票即被脚本批量买走,二级市场加价数倍 | Ticketmaster「约 60% 门票被机器人买走」出自 Vice 2018【新闻/第三方报道,新闻口径】;大麦 2026-10 热门场次「想看 500 万+ vs 票量 2.2 万张」【新闻/第三方报道】;Queue-it「常态约 40%、热门 60–90% 为恶意机器人流量」是**流量口径**、厂商自报【报告/机构,⚠️ 不与「票被买走」混用】 | 每钱包限购 + **商家可选预存门槛**(F-27)提高小号成本 |
| **P-B 假票与截图伪造** | 静态电子票截图可复制传播,门口难辨真伪 | SafeTix 约 15 秒旋转条码 + 「Screenshots won't get you in」【官网宣称】;大麦动态二维码约 30 秒刷新【新闻/第三方报道】;Feulner 等 2022 指出动态码+实名可被「共享账号/共享 SIM」绕过【论文/学术】 | ERC-721 唯一所有权 + **票据溯源**(F-28):发行方与每次钱包变更可查 |
| **P-C 双重入场(一票多用)** | 同一张票被多人先后使用,或转售后原票仍可入场 | 大麦「每码仅兑换一次」【新闻/第三方报道】;学术与行业实践均把「核销一次」作为最低要求 | 验票链上永久打标 `used[tokenId]`,重复入场被合约拒绝(F-13) |
| **P-D 不透明、不可独立验证** | 观众无法验证「这张票是否有效/是否被用过/是否真的属于我」 | 二级市场三种治理答案(StubHub 自由加价 / 摩天轮折扣赔付 / Tixel 硬性 +10%)均依赖平台规则,见 02 §6.1【官网宣称/新闻】;Regner 等 ICIS 2019 认为 NFT 可改进二级市场控制,代价是 gas/延迟/隐私【论文/学术】 | 公开可验证的票面状态机 + 溯源视图 + 任何人可查的链上日志 |

> **结构性原因**:中心化票务数据库中,规则、票面、验票记录都由平台单方维护——平台可以改规则、可以回滚打标、观众无法独立复核。智能合约把「规则」和「状态」放到公开账本上,这是 LivePass 的出发点,也是 §8 定位推导的起点。

## 1.2 链上能带来什么:从「三个机制」到「三项可配置/可验证设计」

| 机制 | 在 LivePass 中的设计落地 | 目标合约接口(实现规格) |
|---|---|---|
| **规则即代码** | 每钱包每场限购一张、支付金额必须等于票价、已验票不可再验、闭锁策略下转移直接 revert——规则由合约执行,前端绕不过 | `buy()` 的 require 链;`verify()` 的 require 链;`transferFrom` 的策略判定(canon §8) |
| **票即资产 + 可验证来源** | 票是 ERC-721 NFT;发行方、首次买家、每次转移都留链上记录,`provenance()` 可查 | `mintHolder`、`TicketIssued`/ERC-721 `Transfer` 日志、`provenance(tokenId)` |
| **状态公开可验证** | 验票 = 链上永久打标;票面艺术随状态变化(S0/S0'/S1/S2) | `used[tokenId]`;`tokenURI()` 的状态分支 |
| **规则可配置(本版新增)** | 商家按演出选择转售策略(Closed/Open/Detect),并可选开启预存门槛;开售前可改、开售后冻结 | `createShow(..., uint8 resalePolicy, uint256 minStake)`;`setResalePolicy`/`setStakeRequirement`(仅开售前);`rulesFrozen`;`stake()`/`unstake()` |

## 1.3 LivePass 是什么(设计描述)

**定位(逐字,canon §3)**:LivePass 是一个「**大麦式体验 + 链上硬保证 + 规则可配置**」的链上演唱会票务 DApp。
**English positioning**:*LivePass is a Damai-style ticketing experience with hard on-chain guarantees and merchant-configurable rules.*

- **三类角色**:主办方(发布演出、配置策略与门槛、开售、验票、提现)、观众(浏览、预存、购票、持票、转售受策略约束)、场馆/验票方(Check 预检 + Verify 打标)。
- **三个「不可能」**(顺序固定,canon §3):**不可伪造**(ERC-721 + 发行方与钱包变更全程上链)、**不可囤积**(每钱包每场限购一张 + 可选预存门槛)、**不可二次使用**(验票链上永久打标)。
- **三条差异化**(顺序固定,canon §3):链上票面状态机、支付+出票原子结算、**商家可配置的链上规则**(转售策略 + 预存门槛)。
- **本版新增的三项设计**(对应 2026-10-19 用户要求 U1–U3):
  1. **F-15 转售策略(Closed / Open / Detect)**:商家按演出选择「禁止转售 / 允许转售 / 转售可查但拒绝入场」,开售后冻结;
  2. **F-27 预存门槛(防机器人,商家可选)**:购票前须向合约预存最低保证金,`minStake=0` 表示关闭;保证金可退还、可设冷却;
  3. **F-28 票据溯源**:每张票记录发行方 `issuer`、首次买家 `mintHolder`、每次钱包变更(ERC-721 `Transfer`),`provenance()` 一次查全。
- **交付方式**:本阶段交付**设计与需求**;合约、前端、部署、验收证据由技术团队 P1–P4 在实现阶段完成(§1.8)。

### 3.6.1 三条关键取舍的推理

1. **为什么把转售做成三策略而不是一刀切**:调研显示二级市场治理是**规则选择**而非技术选择——GUTS 固定价、Seatlab 不可转移、Ticketmaster 转移重发码、Tixel 硬性 +10%、StubHub 自由加价,分别代表「禁转/限转/重签/限价/自由」五种答案(01/02 号文档)。一刀切必然得罪一类主办方:音乐节可能希望转售流动,剧场可能希望完全禁转。**结论**:把选择权交给商家(Closed/Open/Detect),规则由合约执行、开售后冻结,兼顾自由与可信。
2. **为什么预存门槛是可选而非强制**:它本质是**提高小号成本**的经济手段,会占用观众资金,且对「真实粉丝」不友好;不同演出的黄牛压力差异很大。**结论**:做成 `minStake` 可配置、`0` 即关闭,并给出冷却与最低值护栏;有效性需实现后实测(风险见 §7.3)。
3. **为什么溯源纳入 MVP**:假票与截图问题的根因是「无法证明票的来源与流转」;ERC-721 本身已有 `Transfer` 日志,`mintHolder` + `provenance()` 只是把「发行方+首购+当前持有人+时间」聚合为可读视图,实现成本低、对防伪叙事价值高。**结论**:必做。
4. **为什么 A 类不写成「不做」**:用户明确希望「尽可能全面」;这些能力有明确价值,但涉及合规/隐私/资金/外部系统,不适合作为 MVP 承诺。**结论**:写成「建议算法团队可选实现」,给价值/风险/依赖/验收建议(§4.3),不做也不影响课程交付。

## 4.1 本期必做功能卡(F-01…F-15、F-27、F-28)

### F-01 发布演出 · 主办方 · M · 本期必做

- **描述**:主办方填写名称、海报、票价(ETH)、**转售策略**、**预存门槛**(可为 0=关闭),调用 `createShow(name,poster,price,resalePolicy,minStake)`;新演出 `saleOpen=false`、`rulesFrozen=false`。
- **用户价值**:零代码上架演出,并在发布时一次配置转售与防机器人规则(对齐大麦/GET/OPEN 商家后台)。
- **规则**:`resalePolicy` 只接受 0/1/2(Closed/Open/Detect),非法值 revert `"Invalid resale policy"`;`minStake` 低于建议下限时前端提示(合约可保留 `MIN_STAKE_FLOOR` 建议值)。
- **验收**:AC-01(部署后基础状态与地址/交易记录进 README);发布后 P-02 出现新演出(AC-17 口径)。
- **边界**:海报为字符串(URL/data URI);`price>0` 作为「演出存在」判据的替代设计需在实现中明确(建议以 `showCount` 判定,避免免费票歧义)。
- **依赖**:F-03、F-15、F-27;P-07。

### F-02 调整票价 · 主办方 · M · 本期必做

- **描述**:主办方调用 `setPrice(showId,newPrice)` 调整票价;**开售后不可改**(`rulesFrozen=true` 时 revert `"Rules are frozen after sale opens"`),发 `PriceUpdated`。
- **用户价值**:主办方在开售前定价;开售后价格稳定,保护已购票者预期。
- **验收**:AC-09(非 owner revert `OwnableUnauthorizedAccount`;开售后改价 revert)、AC-33(冻结规则);价格展示与 wei 一致(AC-25)。
- **边界**:调价不退款、不改已售订单;`PriceUpdated` 供前端刷新。
- **依赖**:F-01、F-08;P-08。

### F-03 开售 / 停售 · 主办方 · M · 本期必做

- **描述**:`openSale(showId)` 将 `saleOpen=true` 且 **`rulesFrozen=true`**(策略与门槛从此冻结);`closeSale(showId)` 停售;均发 `SaleToggled(showId,open)`。
- **用户价值**:控制开票节奏;开售后规则冻结,观众可预期。
- **验收**:AC-03(开售状态 + `SaleToggled`);停售后 `buy()` revert `"Sale is not open"`(AC-02 口径)。
- **边界**:停售不影响已售票的验票与策略;再开售不解除冻结(设计选择,需在 README 说明)。
- **依赖**:F-01、F-09;P-08。

### F-04 票房提现(不含保证金池) · 主办方 · M · 本期必做

- **描述**:`withdraw()` 将 **`ticketRevenue`(票款)** 转给 owner,发 `Withdrawn(to,amount)`;**保证金池 `totalStaked` 不可被 owner 提取**(资金隔离不变量:`balance == ticketRevenue + totalStaked`,见 §6.8),观众可 `unstake` 取回。
- **用户价值**:票房回到主办方;保证金安全,避免商家卷走预存款。
- **验收**:AC-11(提现后 `ticketRevenue==0`、owner 余额增加、`balance==totalStaked`、`totalStaked` 不变)、AC-26(仅 owner 可提)。
- **边界**:无部分提现(实现可扩展);`transfer` 固定 gas 限制;资金隔离是安全红线(§7.3 RSK-04;不变量与 02-requirements §4.9/TC-13 对齐)。
- **依赖**:F-09、F-27;P-10。

### F-05 主办方概览 · 主办方 · M · 本期必做

- **描述**:四块口径(AC-29):演出数=`showCount()`;售票数=`TicketBought` 事件计数(从部署区块起分块);成交额=Σ成交价;**可提现=`ticketRevenue`(票款)**;保证金池=`totalStaked` 单列只读(不可提,见 §6.8 资金隔离不变量)。
- **用户价值**:一眼看到经营数据,并区分「历史成交」「账上可提票款」「保证金池」。
- **验收**:AC-29(四口径与链上一致、刷新一致)、AC-28(刷新重读)、AC-17(演出数一致);AC-11(提现只动票款)。
- **边界**:事件计数禁止硬编码窗口,须从部署区块分块;RPC 限制时可退化展示并标「估算」(该情形 AC-29 记未通过并登记环境限制)。
- **依赖**:F-01、F-09、F-27;P-10。

### F-06 演出海报墙 · 观众 · M · 本期必做

- **描述**:演出卡片网格:海报、名称、票价、开售状态、**转售策略徽标**(禁转/可转/检测)、**预存要求徽标**(需预存 X ETH / 无需预存)。

- **验收**:AC-17(渲染 `showCount()` 条,字段与链上一致)、AC-25(价格 wei 一致)。
- **边界**:无搜索/筛选(F-21 后续);海报加载失败需占位图;空态见 P-11(AC-22)。

- **描述**:大海报、名称、票价、开售状态、**转售策略说明**、**预存门槛说明与当前资格状态**、Buy 按钮;若需预存则引导 P-12。
- **用户价值**:购票决策页,规则透明。
- **验收**:AC-18(展示票价/策略/门槛);AC-02/04/06(购票失败提示)。
- **边界**:演出不存在显示 P-11 错误态;策略解释文案需产品提供(§5.4 P-03)。
- **依赖**:F-06、F-09、F-15、F-27;P-03。

### F-08 钱包连接与角色路由 · 全体 · M · 本期必做

- **描述**:登录页连接 MetaMask → 校验/切换 Sepolia → 读 `owner()` 路由:owner→控制台,其他→观众端;监听 `accountsChanged`/`chainChanged`。
- **用户价值**:一个入口区分角色;网络/账户变化有明确处理。
- **验收**:AC-12(未连接不发交易)、AC-13(非 Sepolia 提示切链,拒绝停留)、AC-16(角色路由)。
- **边界**:未装 MetaMask 提示安装;切账户后需重新读链;不引入后端会话。
- **依赖**:全部;P-01。

### F-09 购票(原子结算 + 每钱包限购 + 精确票价) · 观众 · M · 本期必做

- **描述**:`buy(showId)` 以精确 `msg.value` 支付;require 链:`saleOpen` → `!hasBought` → `msg.value==price` →(若 `minStake>0`)`stakeOf>=minStake` 且冷却已过;成功后铸造 NFT 给买家,写 `mintHolder`/`hasBought`/`ticketOf`/`tokenShow`,发 `TicketBought`。
- **用户价值**:本产品的核心动作——支付与出票同一笔交易;限购与门槛由合约强制。
- **验收**:AC-02(未开售)、AC-04(金额不符)、AC-05(正常购票全字段)、AC-06(重复购票)、AC-24(不同演出各一票)、AC-25(价格精度)。
- **边界**:预存不足/冷却中分别 revert(`"Insufficient stake"`/`"Stake cooling down"`);`tokenId` 全局自增与票号 `ticketOf` 不同(§7.2 B-02)。
- **依赖**:F-03、F-08、F-11、F-27;P-03/P-04。

### F-10 我的票夹 · 观众 · M · 本期必做

- **描述**:按**所有权枚举**(非购买记录)展示当前钱包持有的票:票号/tokenId、演出名、状态徽标(S0/S0'/S1/S2)、策略徽标、溯源入口、Etherscan 链接。
- **用户价值**:票真正在用户钱包里,状态与来源可查(区别于平台票夹)。
- **验收**:AC-19(只显示当前持有)、AC-21(验票后状态变化)、AC-28(刷新重建)。
- **边界**:所有权枚举用 `Transfer(null,wallet)` 从部署区块分块 + `ownerOf` 校验;无分页;无转售挂单(F-16 后续)。
- **依赖**:F-09、F-11、F-28;P-05。

### F-11 链上 SVG 票面 · 全体 · M · 本期必做

- **描述**:`tokenURI(tokenId)` 在合约内拼 SVG → base64 `data:application/json;base64,...`;票面含演出名、票号、持有人、网络、状态行;**状态由策略与 used 决定**:S0 `UNUSED · VALID` / S0' `TRANSFERRED · ADMISSIBLE` / S1 `VERIFIED · ADMIT` / S2 `RESOLD · NOT ADMISSIBLE`。
- **用户价值**:票面艺术 = 状态机,无需外部图床;状态与策略差异直观可见。
- **验收**:AC-10(合法 JSON + base64 SVG,含演出名/票号/持有人/状态)、AC-21(验票后文案变化)。
- **边界**:SVG 固定尺寸;演出名需做 JSON/SVG 转义(开放问题 OQ-05);文案两种写法:SVG 用连字符、文档用间隔号(§10-C)。
- **依赖**:F-09、F-13、F-15;P-05/P-06。

### F-12 验票预检 Check · 场馆 · M · 本期必做

- **描述**:输入 showId+tokenId 后 Check:读 `ownerOf`/`used`/`tokenShow`/策略与 `mintHolder`,零 gas 输出持有人、使用状态、**策略判定**(该票按当前策略能否入场)与原因。
- **用户价值**:验票前先查后放行,零 gas、零等待;避免门口才发现策略违规。
- **验收**:AC-20(零 gas 返回持有人+使用状态+策略判定)。
- **边界**:票不存在/不属于该场给出明确提示;Check 只读,不改变状态。
- **依赖**:F-10、F-13、F-15;P-09。

### F-13 链上验票 Verify · 场馆 · M · 本期必做

- **描述**:`verify(showId,tokenId)`(owner 或一次性授权):校验票属于该场、未使用,并按策略判定(Detect 下非首购持有人 revert `"Resale not permitted"`)→ `used[tokenId]=true` → 发 `TicketVerified`;票面变 S1。
- **用户价值**:双重入场在链上不可能;策略违规票在门口被拒绝。
- **验收**:AC-07(成功打标+事件)、AC-08(重复验票 revert `"Ticket already used"`)、AC-09(非授权 revert)、AC-27(前端解码 revert)。
- **边界**:Closed 策略下不存在转手票;Open 策略下任意持有人可入场;Detect 下仅首购持有人可入场。
- **依赖**:F-03、F-09、F-12、F-15;P-09。

### F-14 验票计数与流程校验 · 场馆 · S · 本期必做

- **描述**:P-09 显示该场已验票数(`TicketVerified` 事件计数,从部署区块分块)与最近验票记录;对失败操作给出流程提示(先 Check 后 Verify)。
- **用户价值**:场馆现场核对入场进度与错误原因。
- **验收**:AC-07(事件计数 +1、重载一致);计数与 `used` 总数交叉校验。
- **边界**:事件计数依赖部署区块;不计入保证金等无关事件。
- **依赖**:F-13;P-09。

### F-15 商家可选转售策略(Closed / Open / Detect) · 主办方 · M · 本期必做

- **描述**:`createShow` 时选择策略:0=**Closed(禁止转售)**——`transferFrom`/`safeTransferFrom` 一律 revert `"Resale not permitted"`,票面不出现 TRANSFERRED;1=**Open(允许转售)**——转移成功,票面 S0' `TRANSFERRED · ADMISSIBLE`,当前持有人可入场;2=**Detect(检测)**——转移成功但票面 S2 `RESOLD · NOT ADMISSIBLE`,`verify()` 拒绝非首购持有人(revert `"Resale not permitted"`);**开售前可通过 `setResalePolicy(showId,policy)` 修改**(发 `ResalePolicyUpdated`;非法值 revert `"Invalid resale policy"`),**开售后冻结**(开售后调用 revert `"Rules are frozen after sale opens"`,AC-33)。
- **用户价值**:把「能不能转售」从平台政策变成商家可配置、合约强制的规则;不同演出各取所需(音乐节可 Open、剧场可 Closed、控价场可 Detect)。
- **验收**:AC-30(Closed 转移 revert、无 TRANSFERRED)、AC-31(Open 转移成功 + S0' + verify 放行)、AC-32(Detect 转移成功 + S2 + verify revert)、AC-33(开售后调 `setResalePolicy` revert `"Rules are frozen after sale opens"`)。
- **边界(必须披露,canon §6)**:①Closed 只阻止合约层转移,无法阻止链下私下交易(卖私钥/助记词)——身份层缺口;②Detect 是「允许转手但拒绝入场」,存在「已验票后再转手」的票面不一致(票面 S2 但已入场),实现中建议禁止验票后转移;③策略开售即冻结;④Open/Detect 不约束成交价格(限价属 F-16 后续)。
- **依赖**:F-01、F-03、F-09、F-13;P-07/P-08/P-09。

### F-27 预存门槛(防机器人,商家可选) · 主办方/观众 · M(功能)/可选(启用) · 本期必做

- **描述**:商家在 `createShow` 设 `minStake`(0=关闭),**开售前可用 `setStakeRequirement(showId,minStake)` 修改**(发 `StakeRequirementUpdated`;开售后 revert `"Rules are frozen after sale opens"`,AC-33);观众在 P-12 调 `stake()` 预存 ETH(记录 `stakeOf`/`stakeSince`,发 `Staked`,更新 `totalStaked`),可 `unstake(amount)` 取回(发 `Unstaked`);`buy()` 时若 `minStake>0` 校验余额与冷却(拒绝 `"Insufficient stake"`/`"Stake cooling down"`)。
- **用户价值**:用资金占用提高机器人/小号的抢票成本,且不强制所有演出启用;保证金可退,资金由合约保管、owner 不可提取。
- **验收**:AC-34(未达门槛购票 revert)、AC-35(预存后购票成功、`stakeOf` 正确、取回后到账)、AC-36(`minStake=0` 无需预存)、AC-37(冷却中 revert)、AC-33(开售后调 setter revert)。
- **边界**:①预存门槛是经济手段,有效性依赖门槛金额与冷却时长(需实测,§7.3 RSK-02);②保证金池与票款隔离(`balance == ticketRevenue + totalStaked`),`withdraw` 不得动保证金;③人人可 stake,不绑定身份(身份缺口);④冷却常量 `STAKE_COOLDOWN`(建议 10 分钟)须写入 README 与 AC-37 说明。
- **依赖**:F-01、F-03、F-09;P-12/P-08。

### F-28 票据溯源(发行方 + 钱包变更链) · 全体 · M · 本期必做

- **描述**:合约在 `buy()` 记录 `mintHolder[tokenId]=buyer`,并发出 **`TicketIssued(showId, tokenId, issuer, buyer)`**(发行时记录 issuer→buyer);发行方通过 **`issuer(showId)`** 查询(= 该演出的发布方,即 `createShow` 调用者);每次所有权变更由 ERC-721 `Transfer` 事件留痕;`provenance(tokenId)` 返回 `(issuer, firstBuyer, currentHolder, mintedAt, used)`;前端在 P-05/P-06 展示「发行方 / 首次买家 / 当前持有人」与链上日志入口。
- **用户价值**:每张票的「出身」与流转历史可查,假票与截图无法伪造来源;满足用户 U3「记录初始归属、每次钱包变化都被记录」。
- **验收**:AC-38(`provenance` 字段与 `TicketIssued`/`Transfer` 日志一致)、AC-39(前端展示发行方/首购/当前持有人,任何人可核对链上日志)。
- **边界**:溯源可查≠阻止转售(策略另行控制);`issuer(showId)` 返回发布方地址,若 owner 转移不影响历史 issuer 认定(需在 README 说明);`mintedAt` 取区块时间戳;`provenance` 实现可用链上数组或"`TicketIssued`+`Transfer` 日志派生",但视图语义不变。
- **依赖**:F-09、F-11、F-15;P-05/P-06。

### P-12 预存与购票资格 · 观众 · 路由 `/stake` · 待实现

- **目的**:让观众理解并完成预存,获得购票资格。

# 6 核心流程与状态机

> 三条主流程(购票/验票/提现)+ 转售策略分支 + 票面状态机 S0/S0'/S1/S2 + 前端交易状态机。
> 状态与接口口径来自 canon v2.0 §6/§8;本阶段全部为**实现规格**。

## 6.1 购票流程(屏幕级)

**路径**:P-01 登录 → P-02 海报墙 → P-03 详情 →(如需)P-12 预存 → P-03 购票 → P-04 交易状态 → P-05 票夹。

| 步 | 页面 | 用户动作 | 前端行为 | 链上行为 | 失败分支 |
|---|---|---|---|---|---|
| 1 | P-01 | 连接钱包 | `eth_requestAccounts` → 校验/切 Sepolia → 读 `owner()` 分流 | 只读 `owner()` | E-01/E-02/E-03 |
| 2 | P-02 | 浏览 | 读 `showCount()`+`shows(i)`,渲染策略/预存徽标 | 只读 | E-13/E-14 |
| 3 | P-03 | 查看详情 | 读票价/策略/门槛/资格;若需预存则显示资格不足 | 只读 | E-13 |
| 4 | P-12(可选) | 存入保证金 | 读 `stakeOf`/`stakeSince`;调 `stake()` | `Staked` 事件,更新 `stakeOf`/`stakeSince` | E-27/E-28/E-10 |
| 5 | P-03 | 点 Buy | 按钮→pending;调 `buy(showId,{value:price})` | require 链 → mint → 并发 `TicketBought` + `TicketIssued`(含 issuer→buyer) | E-02/E-04/E-05/E-06/E-25/E-27/E-28 |
| 6 | P-04 | 等待确认 | pending 显示哈希;确认后重读 | 区块确认 | E-14/E-19 |
| 7 | P-05 | 查看新票 | 票夹出现 S0,可查溯源 | — | E-22/E-23 |

**关键不变量**:支付与出票同一笔交易;每钱包每场限购一张;`msg.value` 必须等于票价;需预存时先满足门槛与冷却。

## 6.2 验票流程(屏幕级)

**路径**:P-09 验票面板 → Check(零 gas,含策略判定)→ Verify(上链打标)→ P-05 票面变化。

| 步 | 页面 | 用户动作 | 前端行为 | 链上行为 | 失败分支 |
|---|---|---|---|---|---|
| 1 | P-09 | 输入 showId+tokenId | 本地校验数字格式 | — | E-11/E-12 |
| 2 | P-09 | 点 Check | 读 `ownerOf`/`used`/`tokenShow`/`mintHolder`/策略,渲染预检 | 无(eth_call) | E-11(票不存在) |
| 3 | P-09 | 点 Verify | 调 `verify(showId,tokenId)` | 权限与策略 require → `used=true` → `TicketVerified` | E-07/E-08/E-12/E-31 |
| 4 | P-09 | 等待确认 | 成功提示;计数 +1 | 区块确认 | E-14/E-19 |
| 5 | P-05 | 刷新票夹 | 读 `used` → 票面 S1 | 状态已上链 | — |

**策略判定规则(Check 与 Verify 一致)**:Closed → 不存在转手票,任何持有人可入场;Open → 当前持有人可入场;Detect → 仅 `ownerOf == mintHolder` 可入场,否则拒绝 `"Resale not permitted"`。

## 6.3 提现流程(屏幕级)

**路径**:P-10 → Withdraw → 票款到账(保证金池不变)。

| 步 | 页面 | 用户动作 | 前端行为 | 链上行为 | 失败分支 |
|---|---|---|---|---|---|
| 1 | P-10 | 查看四块 | 读 AC-29 四值 + 保证金池(只读) | 只读 | E-14/E-17 |
| 2 | P-10 | 点 Withdraw | 按钮禁用 + 调 `withdraw()` | 票款 → owner,发 `Withdrawn` | E-10/E-17 |
| 3 | P-10 | 等待确认 | 成功提示;可提现归 0,成交额不变 | 区块确认 | E-14/E-19 |
| 4 | Etherscan | 核对 | 外链 | 票款余额=0,保证金池不变 | — |

**资金隔离(安全红线)**:`withdraw()` 只能提取 `ticketRevenue`(票款);`totalStaked`(保证金池)不可被 owner 提取。不变量 `address(this).balance == ticketRevenue + totalStaked` 必须在 `stake/unstake/buy/verify/withdraw` 后成立(变量与守恒式见 §6.8;与 02-requirements §4.9/TC-13 对齐;§7.3 RSK-04)。

## 6.4 转售/转移流程(按 F-15 策略分支)

| 策略 | 触发 | 合约行为 | 票面结果 | 入场判定 |
|---|---|---|---|---|
| **Closed** | 持有人发起 `transferFrom`/`safeTransferFrom` | revert `"Resale not permitted"` | 无变化(不出现 TRANSFERRED) | 原始买家可入场 |
| **Open** | 持有人发起转移 | 转移成功,所有权变更 | S0' `TRANSFERRED · ADMISSIBLE` | 当前持有人可入场 |
| **Detect** | 持有人发起转移 | 转移成功,但 `verify()` 拒绝非首购持有人 | S2 `RESOLD · NOT ADMISSIBLE` | 仅原始买家可入场;他人 verify revert |

**前端行为**:P-06 展示该票受哪条策略约束;Closed 时隐藏/禁用转移入口;Open/Detect 时展示转移入口并提示后果;策略在开售后冻结,不可改。

## 6.5 票面状态机(canon §6,唯一口径)

| 状态 | 票面文案 | 判据 | 入场 | 可达策略 |
|---|---|---|---|---|
| **S0** | `UNUSED · VALID` | 未验票,且(当前持有人 = 首次买家 或 策略为 Open 且尚未转移) | ✅ | Closed / Open |
| **S0'** | `TRANSFERRED · ADMISSIBLE` | 未验票且当前持有人 ≠ 首次买家 | ✅ | Open |
| **S1** | `VERIFIED · ADMIT` | 已验票(`used=true`) | 已入场 | Closed / Open / Detect |
| **S2** | `RESOLD · NOT ADMISSIBLE` | 未验票且当前持有人 ≠ 首次买家 | ❌(verify revert `"Resale not permitted"`) | Detect |

```text
购票成功(铸造给买家)
        │
        ▼
S0  UNUSED · VALID ──verify()──▶ S1  VERIFIED · ADMIT(永久)
   │
   ├─ Closed:任何 transfer 被 revert(保持 S0)
   ├─ Open:  transfer 成功 → S0' TRANSFERRED · ADMISSIBLE ──verify()──▶ S1
   └─ Detect:transfer 成功 → S2  RESOLD · NOT ADMISSIBLE(verify 拒绝)
```

**必须披露的设计边界(canon §6)**:
1. **Closed 只在合约层阻止转移**:链下私下交易(卖出钱包私钥/助记词)无法阻止——这是身份层缺口(§8.7 边界 1);
2. **Detect 是「允许转手但拒绝入场」**:存在「已验票后再转手」的票面不一致(票面 S2 但已入场),实现中**建议禁止验票后转移**(见 §7.3 RSK-03);
3. **策略与预存门槛在开售后冻结**(`rulesFrozen`),避免商家临时改规则影响已购票者;
4. **Open/Detect 不约束成交价格**:限价属 F-16(后续/建议),本期不承诺价格上限。

## 6.6 状态迁移与边界表

| 迁移 | 触发 | 前置条件 | 后置 | 失败行为 | 回滚 |
|---|---|---|---|---|---|
| ∅→S0 | `buy()` 精确支付 | 开售、未购过、(如需)预存达标且冷却已过 | S0;`mintHolder`/`hasBought`/`ticketOf`/`tokenShow` 写入 | 5 类 revert(AC-02/04/06/34/37) | 整笔回滚 |

| S0→S0'(Open) | `transferFrom` | 持有人授权 | S0' | — | 转账成功即生效 |
| S0'→S1(Open) | `verify()` | 同上,当前持有人可入场 | S1 | revert | 回滚 |
| S0→S2(Detect) | `transferFrom` | 持有人授权 | S2(仅票面/验票判定) | — | 转账成功 |

## 6.7 前端交易状态机

```text
idle ─点击─▶ signing(等签名) ─确认─▶ pending(已广播) ─▶ confirmed(刷新数据)
                 │                        │
                 └─拒绝─▶ cancelled        └─错误/超时─▶ failed(可重试)
```

| 状态 | 界面 | 按钮 | 动作 |
|---|---|---|---|
| idle | 正常 | 可点 | 发起 |
| signing | `Waiting for MetaMask…` | 禁用 | 拒绝→cancelled |
| pending | `Confirming…` + 哈希链接 | 禁用 | 超时可重试(先查 receipt) |
| confirmed | 成功 + 哈希 | 恢复 | 刷新链上数据 |
| failed | 解码后的 revert | 恢复 | 重试 |
| cancelled | 「已取消」 | 恢复 | 重试 |

**错误解码**:优先 `e.shortMessage`,其次 `e.reason`,最后 `e.message`;去掉 `execution reverted: ` 前缀;无法解码时显示原文 + Etherscan 核对提示。

## 6.8 目标合约接口契约摘要(canon §8,供 P1 实现)

> 本阶段合约尚未实现;以下是**目标接口**,实现时签名可微调但**语义与 revert 文案不得变**。完整契约见 02-requirements §4。**参数类型从略处以 canon §8 逐字为准**(如 `createShow` 的 `string/string/uint256/uint8/uint256`);事件/函数命名同理。

**口径说明**:①`issuer(showId)` = 该演出的发布方(`createShow` 调用者),`provenance` 的 issuer 取此值;②`TicketIssued` 在 `buy()` 铸造时发出,与 `Transfer(0→buyer)` 共同构成溯源日志;③所有 revert 文案逐字实现,前端据此解码(AC-27)。

**常量建议**:`STAKE_COOLDOWN`(建议 10 分钟)、`MIN_STAKE_FLOOR`(建议 0.001 ETH);实现时定值但须写入 README 与 AC-37 说明。

**实现顺序**:最小闭环(`createShow`→`openSale`→`buy`→`verify`→`withdraw`)→ 策略(F-15)→ 预存(F-27)→ 溯源(F-28)→ 前端页面完整接线。

## 6.9 端到端时序(文字)

```text

    │                          │ ←──── stake() 预存(如需) ──────────── │
```

## 7.2 边界条件(B-01…B-12)

| # | 边界 | 事实/规则 | 设计含义 |
|---|---|---|---|
| B-01 | 金额精度 | 0.01 ETH = 10^16 wei;1 wei = 10^-18 ETH | 前端一律 `parseEther/formatEther`,禁止浮点运算 |

# 8 产品定位与竞品差异

> 本节是报告 1.2.5「从调研到产品定位」的中文底稿。**写法:证据 → 推理 → 结论**;放弃项一律用产品理由(合规/隐私/复杂度/成本/风险),不使用内部课程语境。

## 8.1 定位结论(先给结论,后文给出推导)

- **一句话定位(逐字,canon §3)**:LivePass 是一个「**大麦式体验 + 链上硬保证 + 规则可配置**」的链上演唱会票务 DApp。
- **English positioning**:*LivePass is a Damai-style ticketing experience with hard on-chain guarantees and merchant-configurable rules.*
- **三个「不可能」**(顺序固定):**不可伪造**(ERC-721 + 发行方与每次钱包变更上链,溯源可查)、**不可囤积**(每钱包每场限购一张 + 可选预存门槛)、**不可二次使用**(验票链上永久打标,重复入场被拒绝)。
- **三条差异化**(顺序固定):**链上票面状态机**、**支付+出票原子结算**、**商家可配置的链上规则**(转售策略 + 预存门槛)。
- **四项诚实边界**:见 §8.7。

### 推理(从证据推出什么)

1. **需求存在且是结构性的**:16 家中 7 家已无法以宣传时的形态存活(4 家停运/注销、2 家产品不复存在、1 家被收购且关停),但传统票务仍在用动态码/实名/限价对抗同一批问题,说明问题真实且未被解决;学术也承认价值但缺端到端验证。
2. **现有链上方案的缺口不在「铸 NFT」,而在**:①身份(一人多钱包);②大众门槛(钱包/私钥);③二级市场治理(要么放任、要么规则不可信);④票的来源与流转不可读(有日志但不友好)。本设计选择在③④做增量:规则可配置 + 溯源可查。
3. **二级市场治理是规则选择,不是技术选择**:StubHub(自由加价)、摩天轮(折扣+赔付)、Tixel(+10% 硬上限)、GUTS(固定价)、Seatlab(不可转移)五种答案都不依赖区块链;链上改变的是「规则由谁执行、能否被单方篡改、能否公开验证」。→ 得出「商家可配置规则」的设计方向。
4. **防机器人不能只靠检测**:检测是军备竞赛(Iliou 等);提高小号成本的经济手段(门槛/预存)与身份核验互补 → 预存门槛作为可选设计。
5. **「最后一公里」不可忽视**:链上无法让非合作闸机作废实体票;本设计只承诺「链上状态与来源可验证」,不承诺跨场馆通用。

### 结论(Step 1 产出)

- **EV-1 需求真实**:黄牛/机器人、假票截图、双重入场、不透明四类痛点均有证据(§1.1)。
- **EV-2 链上增量明确**:凭证唯一 + 状态不可回滚 + 规则可编程/可配置 + 公开可验证 + 来源可查;身份/法币/动态码是弱项。
- **EV-3 差异化只能选「链上能做到极硬」的三件事**:状态机、原子结算、可配置规则。
- **EV-4 治理是选择**:转售与门槛应由商家配置,合约执行且冻结。
- **EV-5 研究空白 = 机会**:端到端机制 + 可配置治理 + 溯源的设计与实现仍稀缺(ICECOS 2024)。

## 8.3 定位推导 Step 2:问题确认(四类痛点 + 现有方案缺口)

### 证据

16 家区块链 + 传统 5 家 + 学术 6+3 条(8.2);用户要求 U1–U3(转售策略/预存/溯源)。

### 推理

| 问题 | 证据 | 现有方案的缺口 | 本设计的回答 |
|---|---|---|---|
| 身份缺口(一人多钱包) | Feulner 2022;GUTS 用实名手机号补;大麦用人脸补 | 链上不存身份;KYC 涉隐私合规 | **不承诺解决**;KYC/实名列为建议可选(F-18/F-32);用预存门槛提高小号成本 |
| 加价转售 | L&R 2014(5%/1/3);Tixel +10%;GUTS 固定价;Seatlab 不可转移 | 一刀切禁转伤主办方;自由加价伤观众;规则由平台单方改 | **三策略可配置**(Closed/Open/Detect)+ 开售后冻结 |
| 假票与截图 | SafeTix 15 秒/大麦 30 秒;Feulner 2022 | 静态 NFT 票面不能防截图,但截图不携带所有权 | **溯源**(来源与流转可查)+ 验票看链上 `used`,不看图片 |
| 双重入场 | 大麦「每码仅兑换一次」;行业共识 | 中心化打标可被平台回滚 | 验票链上永久打标(F-13) |
| 机器人抢票 | TM 60%(Vice 2018,新闻口径);Queue-it 流量口径;检测类论文 | 检测可被规避;限购可开多钱包 | 每钱包限购 + **可选预存门槛** |

**被证伪的两个「想当然」**:
1. **「上链就能消灭黄牛」——证伪**:GET/OPEN、GUTS 仍需实名与法币;Tixel 无区块链也能限价+原票作废;YellowHeart/Seatlab 有链上票却停运。→ 链上压缩套利空间,不消灭黄牛;不承诺「零黄牛」。
2. **「大众用户愿意自管私钥」——证伪**:GET/OPEN 钱包对用户隐形、Oveit 代铸+钱包后置、Tixel 无钱包。→ 本设计面向愿意用钱包的用户;钱包抽象列为建议可选(F-26)。

### 结论(Step 2 产出)

可做且合约能保证的:限购、精确票价、原子结算、验票打标、三策略、预存门槛、溯源。
不可由合约单独解决的:身份、法币、动态码服务端、跨场馆、争议赔付 → 列为建议可选/后续,并写入诚实边界。

## 8.4 定位推导 Step 3:设计原则(三条)

### 证据

Step 1–2 的结论 + 调研中的机制对照(GUTS/Seatlab/TM/Tixel/大麦)。

### 推理

1. **规则上链**:把「能不能转售、要不要预存、一张票只能买一次、验过不能再验」写进合约,商家按演出配置,合约执行、开售后冻结 → 解决「规则由平台单方改」的不信任问题。
2. **状态可见**:票面状态机(四态)+ 溯源(发行方/首购/当前持有人)让「票是否有效、从哪来、到过谁手里」一眼可查 → 解决不透明。
3. **门槛可配**:同一套合约同时服务「高需求控价场」(Closed/Detect + 预存)与「开放流动场」(Open) → 解决「一刀切治理」的产品不适应性。

### 结论

三条设计原则直接映射为差异化:链上票面状态机、支付+出票原子结算、商家可配置的链上规则;并由 F-15/F-27/F-28 承载。

## 8.5 定位推导 Step 4:定位(候选比较 + 反事实检验)

### 证据

Step 1–3 结论;调研中的形态对照(白标基础设施 / Web3 原生市场 / 传统平台 / 大厂实验)。

### 推理(三选一)

| 候选 | 需要的能力 | 证据判断 | 结论 |
|---|---|---|---|
| 「另一个大麦」(强实名+风控+选座+支付) | 中心化身份、风控、支付、运营 | 大麦三合一/0.75 秒是中心化能力;合规与成本高,不是链上能复制的 | ❌ 放弃 |
| 「纯 Web3 原生市场」(Seatlab 型:NFT+二级+限价+版税) | 完整二级市场、身份、流动性 | Seatlab 停更、YellowHeart 停运;完整市场需要托管/争议处理,复杂度高 | ❌ 放弃 |
| **「大麦式体验 + 链上硬保证 + 规则可配置」** | 成熟 UX + 链上能做硬的三件事 + 商家可配规则 | GET/OPEN、GUTS 证明「体验+链上」可落地;规则可配置是治理差异化的自然延伸 | ✅ 选择 |

**反事实检验(去掉任一要素,定位是否还成立?)**:
- 去掉**状态机/溯源** → 票只剩所有权,「有效性与来源可见」要靠前端自证,差异化消失;
- 去掉**原子结算** → 出现「付款后等待出票」的中间态,与中心化票务无区别;
- 去掉**可配置规则** → 转售与门槛只能一刀切,无法同时服务控价场与开放场,治理叙事不成立。
→ 三者缺一不可,因此差异化按「状态机 → 原子结算 → 可配置规则」固定顺序。

### 结论(Step 4 产出)

1. **定位(逐字,canon §3)**:「大麦式体验 + 链上硬保证 + 规则可配置」的链上演唱会票务 DApp。
2. **三个不可能**(§8.6)、**三条差异化**(§8.6)、**四项诚实边界**(§8.7)。
3. **三项新增设计**:F-15 转售策略、F-27 预存门槛、F-28 溯源。

## 8.8 诚实边界四条(canon §3,必须逐条出现)

1. **身份层:一人可开多钱包,链上不存身份;KYC/实名+人脸属建议可选能力(见 §4.3 A 类),不作为本设计承诺。**
   - 后果:开多个钱包仍可多买;限购与预存只提高成本,不解决身份。
   - 处理:F-18/F-32 写成建议可选;报告与 README 明确披露。
2. **资金:Sepolia 测试网,无真实资金。**
   - 后果:不能服务真实消费者;「买票」用测试 ETH,无货币价值。
   - 处理:页面与文档标注测试网;不接法币(F-26 为建议可选)。
3. **场馆:若实现为 `onlyOwner` 验票,须写入边界(单一管理员钱包模拟闸机)。**
   - 后果:验票权限集中;不是真实场馆系统。
   - 处理:README/报告如实说明;独立角色/一次性授权列为实现选择与建议(OQ-04)。
4. **生态:不承诺跨场馆互认;让非合作闸机作废实体票非本设计目标。**
   - 后果:「链上票能否过闸机」仍由出票方与场馆认定。
   - 处理:定位只承诺「链上状态与来源可验证」,不承诺生态级互认。

## 8.10 区块链补了什么、没补什么(与中心化方案对照)

| 需求 | 中心化解法(大麦/SafeTix/摩天轮/StubHub/Tixel) | 链上解法(GET/OPEN、GUTS、本设计) | 结论 |
|---|---|---|---|
| 防伪造 | 动态码/旋转条码/扫描核验(依赖平台) | NFT 唯一 + 溯源 + 公开验证 | 都能做到;链上**可公开验证**、不依赖机构 |
| 防一票多卖 | 中央数据库唯一性 + 转移重发码 | NFT 所有权唯一 + 转移留痕 | 都能做到;链上历史人人可查 |
| 防双重入场 | 每码兑换一次(数据库打标) | 验票链上永久打标 | 都能做到;链上打标**不可回滚** |
| 防囤积 | 强实名/人脸;「先有票」+风控 | 每钱包限购 + 可选预存门槛 | 中心化管**身份**更强;链上管**钱包** + 提高小号成本 |
| 限价/转售治理 | Tixel 硬性 +10%(平台规则);GUTS 固定价;Seatlab 限价 | 商家三策略 + 开售后冻结(规则即代码) | 链上规则**不可单方篡改**;价格上限属 F-16 后续 |
| 票源/流转可查 | Tixel 一级直连原票作废 | `provenance` + `Transfer` 日志 | 链上无需一级系统配合;但无法让非合作闸机作废实体票 |
| 可编程/可配置规则 | 平台后台配置(可改) | 合约硬编码 + 商家按演出配置 + 冻结 | 链上规则可信;代价是不灵活(售后能力列建议可选) |

**结论**:补**防伪、留痕、可编程/可配置规则、公开可验证、溯源**;没补**身份、法币支付、场馆配合、争议赔付、跨场馆互认**。这正是 §8.7 四条边界与 §8.11 取舍的来源。
